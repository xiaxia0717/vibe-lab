网速表情屏 · v2 优化方案与实测报告

设备 Unisoc UDX710 随身 WiFi · 240×320 RGB565 小屏  |  2026-09-27

先说结论：你说的"不小的问题"里，两个是致命 bug（表情画反了、原厂时钟每分钟往脸上盖黑块）， 另外还有一批信息是假的或缺失的。v2 已经全部改完、在真机上跑通并实测过了。

1问题定位：v1 到底错在哪

1.1 表情画反了 —— 这是最刺眼的那个

v1 画嘴用的是 arc() 的 upper 参数。屏幕坐标里 y 向下增大， upper=True 取的是圆心上方那半圈，画出来是 ⌒（哭）。v1 在"网速快"的分支里 传了 upper=True，所以 —— 网速越快，脸越哭。

同一个参数错误还造成了第二个 bug：慢速分支的哭弧半径给到 42、圆心又压得太低， 弧底直接冲出脸盘、糊在下面的数字上。

1.2 原厂时钟每分钟往脸上盖一块黑

设备上跑着原厂 UI /usr/bin/lcd -platform linuxfb，它其实就是一个黑底白字的时钟：

它每分钟重绘一次自己。问题在于它是先铺一块不透明的黑矩形再写白字， 这块黑矩形正好横穿表情屏的脸部。实测抓到了这个动作：

采样时刻脸部区域内纯黑像素数判定
t = 146.8 s4 765CLOCK-OVERLAY
t = 206.7 s4 905CLOCK-OVERLAY
t = 263.6 s4 819CLOCK-OVERLAY

约每 60 秒一次，持续不到 1 秒 —— 这就是你看到"脸被切掉一块"的来源。 v1 没有任何应对，只能等自己下一次刷新（1 秒后）才盖回去。

1.3 信号格数根本是编的

v1 的 sig 是用下载速度反推的：sig = 4 if down >= 10 else ...。 也就是说"信号满格"只代表网速快，跟真实信号强度毫无关系。设备其实有真数据，v1 没去读。

1.4 性能：真正贵的地方不是"画"，是"把画翻译成字节"

v1 每帧用 ''.join([chr(v&255)+chr(v>>8) for v in buf]) 把 76 800 个颜色整数拼成字节流。 实测这一句吃掉 33.3 ms，而真正写进 /dev/fb0 只要 0.064 ms —— 99.8% 的时间花在了自己翻译，不是花在硬件上。在只有 2 个核、1.35 GHz 的 SoC 上，这是实打实的负担。

顺手挖出来的一件事：这块屏一直没告诉你，设备其实在过热边缘

设备的温控配置是这样的：

  • 70 °C —— 一级被动降频线（trip_point_0_temp = 70000）
  • 85 °C —— 二级被动降频线
  • 110 °C —— 关机保护线

而 SoC 温度（zone0 / apcpu0 / nrcp / pa5g）实测常年 72–77 °C，已经在降频线之上。 原厂界面只显示电池温度（46 °C，也就是 zone9），所以你从界面上永远看不出 SoC 已经烫了。

但这条因果链后来被数据否掉了。我专门跑了 5 分钟关联采样，把延迟和 SoC 温度、CPU 频率、 下载速率逐项做相关分析 —— 延迟与 CPU 频率的相关系数只有 −0.015，基本等于无关（详见 3.5）。 修正后的结论是：设备确实长期在降频线之上（所以 v2 会把它标红显示，这是事实，值得知道）， 但你的"卡一下"不是它造成的。

v1 的"编码 + 写屏"是由整帧减去绘制推出的（0.197 − 0.118）： v1 那版报告里单独测到的打包耗时是 0.250 s，口径不同，这里统一成"整帧 − 绘制"以便和 v2 对齐。

3.1 整帧 197 ms → 20.4 ms：分三步，每步都量过

不是靠调参数提速的，是三次结构性改动。三组数字都在同一台设备、同一套测试脚本下取得， 每档测 3 轮取最小值，避免频率波动干扰：

阶段整帧 render()相对上一步做了什么
v2 第一版71.70 ms— 基线：帧缓冲是 int 列表，画圆用 O(r²) 逐像素双层循环
② 环形 / 弧线改按行切片48.50 ms快 1.48× 用缓存的"每行半宽表"算出内外半径边界，一行一次切片赋值，替掉逐像素写
③ 帧缓冲改 bytearray20.37 ms快 2.38× 把"翻译"这一步整个删掉（见下）

第 ② 步单独看非常夸张：画那张直径 124 px 的脸盘外圈，从 18.18 ms 掉到 1.21 ms（14.7×）； 浅笑那条弧线从 7.44 ms 掉到 0.44 ms（17.1×）。但整帧只快了 1.48× —— 因为绘制原语只占整帧的一部分，另一大半是下面这件事。

③ 真正的大头：把"翻译"这一步整个删掉

原来每画完一帧，都要把 76 800 个颜色整数重新翻译成字节。实测这个翻译占 33.3 ms， 而把这 153 600 字节真正写进 /dev/fb0 只要 0.064 ms —— 翻译占了 99.8 %，硬件只占 0.2 %。

所以做法不是"翻译得更快"，而是根本不要翻译：帧缓冲直接就是一个 bytearray， 所有绘制原语（矩形、圆、环、弧线）写入的都是已经编码好的 2 字节小端串。 写完就是可以直接落盘的字节，flush() 只剩一句 os.write(fd, buffer(fb))。

打包方案耗时结果
原来的 join(map(...)) 逐像素查表33.28 ms弃用
struct.pack 分块（备选方案）17.31 ms弃用
pack_into 复用 bytearray（备选方案）16.93 ms弃用
直接不翻译（最终采用）0.064 ms采用

顺带还有个副作用：整屏清屏从 buf[:] = BGFILL（1.22 ms）变成 fb[:] = 预编码背景串（0.099 ms），因为后者是一次纯 C 的内存拷贝。

怎么保证"快了但没画错"

这类重构最怕画面悄悄变了。所以写了一个逐字节等价性测试：参照实现仍用重构前的旧代码 （几何算到 int 列表里再编码），新实现直接产出 bytearray，两者逐字节比对。 覆盖 41 个手写用例（四个边角裁剪、圆环退化、抗锯齿边缘、横向裁剪的弧线、单像素矩形等）， 外加 8 901 次随机模糊测试（半径 2–70、圆心含负坐标与越界、随机裁剪窗口）：0 处不一致。 唯一有差异的是"厚度 > 半径"这种退化参数，而代码里所有调用点都是严格"厚度 < 半径"，走不到那里。

3.2 覆盖修复的验证

验证方式是：正常渲染一帧 → 手动往 framebuffer 里写一块黑（模拟原厂时钟）→ 看能不能发现 → 看能不能修好。

然后是实机长时间验证。设备上的 /tmp/face_repair.log 会记下每一次真实发生的覆盖与修复。 连续跑约 9 分钟，抓到 9 次：

那个 121 秒不是漏修 —— 是那一次时钟刚好落在常规渲染的那一瞬间， 被渲染本身盖掉了，所以探测环节没机会记一笔。两条路都是好的： 要么常规渲染顺手盖掉，要么探测在 0.125 秒内盖掉，不存在放任不管的情况。

再换个角度交叉验证：用另一个独立进程以 0.15 秒的间隔连读 95 秒 framebuffer， 数"脸部区域出现纯黑"的采样点：

samples=548    overlay_samples=1    worst_black=1742

548 次采样里只有 1 次看到黑块 —— 它确实每分钟来一次，但每次最多只存在 0.125 秒 就被盖回去了（占 0.18 % 的时间）。v1 没有这个机制，黑块会一直留到自己下一次刷新（最多 1 秒）。

上面这组数据是"每秒探测 8 次"那版测的。探测换成 C 层字节比较之后，单次只要 0.081 ms （原来的 Python 抽样循环是 3.5 ms，快了 43 倍），于是探测频率提到了 33 次/秒， 黑块最长可见时间从 0.125 秒进一步压到 0.030 秒 —— 只剩原来的一成多，肉眼基本抓不到。

3.3 延迟怎么测的（以及为什么必须异步）

设备上有 /bin/ping，但 Python 环境里没有 subprocess、也没有 socket， 只有 os.popen 和 os.system。直接用同步调用有个坑： 对端不回包时它会阻塞整整 1.01 秒 —— 足够让原厂时钟在脸上停留一秒， 把刚做好的覆盖修复机制整个抵消掉。

做法是异步打点：os.system('ping … &') 把 ping 丢到后台， 实测 0.004 秒就返回；8 秒后的下一轮再回来读结果。

调用方式返回耗时
os.system('ping -c 1 -W 1 …')1.01 s（对端不回包时）
os.system('ping -c 1 -W 1 … &')0.004 s

流量代价：每 8 秒一个包，约 63 KB/小时，可以忽略。

3.4 顺手抓到一个每 5 秒烧掉 2.6% CPU 的空操作

整帧从 197 ms 压到 20 ms 之后，进程的常驻 CPU 却还有 8.0%（单核）。 按理说每秒只渲染一次、探测 33 次，不该这么高。所以给真实主循环里每个函数都包了一层计时， 把花销逐项拆开（设备上的 Python 没有 cProfile，只能这么干）：

函数ms/s占比单次
render()32.253 %约 34 ms
fb_stale()18.430 %0.607 ms
read_netdev()2.85 %2.9 ms
ping_async()2.85 %18.5 ms
read_temp() + read_temp_soc()3.05 %2.7 / 0.5 ms

其它0.71 %—

最扎眼的是 bl_on()：它单次就要 135.6 ms。把它拆开看：

对背光节点的操作耗时说明
open 后直接 close，不写0.025 ms打开本身几乎免费
读回当前值5.2 ms可接受
写入 '1'129.8 ms贵的是 write

这个节点是显示控制器 SPI 总线后面的一个 GPIO，驱动在写回调里做同步事务加稳定延时。 而原来的代码为了"保底别黑屏"，每 5 秒无条件写一次 '1'： 135.6 ms × 0.2/s = 27.1 ms/s = 2.7% 的核，全部花在把一个本来就亮着的背光再点亮一次。

改成先读、只在真的灭了才写（读只要写的 1/25）：

fd = os.open(BL, os.O_RDONLY)
v = os.read(fd, 8)
os.close(fd)
if v.strip() == '1':          # 已经亮着，什么都不做
    return
# 否则才走写入路径

同一轮还顺手改掉一个：read_temp() 读一次电池热区要 2.7 ms （走 I2C 到电量计），却每 1 秒调用一次去取一个按分钟变化的值 —— 改成 5 秒一次。 两项合起来省下约 3 % 的单核占用。

一个值得记住的教训：静态微基准和现场数据能差 7 倍

拆表之前，单独测 fb_stale() 是 0.081 ms， 放进真实主循环却是 0.607 ms（7.5×）；render() 单独测 20.4 ms， 现场是 34.3 ms（1.7×）。原因是主循环 99% 的时间在 sleep， interactive 调频器早把频率压到最低档（256 MHz），真正干活时才被唤醒； 而紧凑循环的基准测试能一直把频率顶在 1352 MHz。 所以"优化前 / 优化后"必须用同一种口径，别拿微基准去和现场数比。

3.5 那个"卡一下"到底是什么造成的（结论和最初猜的不一样）

这一节回答你最开始的问题。我跑了一次 5 分钟、每 3 秒一条的关联采样，同时记录： ICMP 延迟、SoC 温度、电池温度、两个核的实时频率、loadavg、瞬时下载速率。共 100 条有效样本。

最初的假设是"SoC 过热降频 → 处理不过来 → 卡"。数据把它否掉了：

相关性皮尔逊 r结论
延迟 ↔ SoC 温度−0.043基本无关
延迟 ↔ CPU 频率−0.015基本无关
延迟 ↔ loadavg−0.152无关
延迟 ↔ 瞬时下载速率−0.121弱

把延迟按 CPU 频率分档看更直观：

CPU 频率样本平均延迟中位最大
256 MHz4833.4 ms30.2 ms111.5 ms
1352 MHz4232.6 ms29.4 ms89.7 ms

CPU 频率在 256 MHz（最低档）和 1352 MHz（最高档）之间来回跳，各占约一半时间 —— 但两种频率下的平均延迟只差 0.8 ms。9 次延迟尖峰（>50 ms）里， 4 次发生在 256 MHz、5 次发生在 1352 MHz，两边一样多。

那"卡一下"是什么？

是空口侧的排队抖动。证据是：整段采样全程 0 丢包，但延迟中位数 28.8 ms、 p90 48.5 ms、最高 111.5 ms —— 这是典型的"包都到了，只是有的在路上排了队"， 不是链路坏了。5G 空口的调度本身就有毫秒级抖动，一旦有突发流量， 上行 ACK 被排在数据后面（bufferbloat）就会让延迟短暂飙高。

另外顺手确认一件事：这台设备的 loadavg 是没用的。整段采样里它恒定在 7.2–7.8， 跟延迟、频率、流量全都不相关。因为卡在 D 状态（不可中断 I/O）的进程也计入 loadavg， 而这个计数被调制解调器的线程长期顶着。所以别拿它判断设备忙不忙。

关于"调到最好性能"这件事，修正后的答案是：CPU 频率不是瓶颈，不值得为它牺牲散热。 设备确实常年 75 °C 以上、在 70 °C 降频线之上（v2 会如实标红显示出来，这值得知道）， 但降频没有让你变慢。真正影响延迟的是空口侧的事，不是这台小机器能调的。

5怎么用

双击 face-control.bat，选 1 启动。它会：

  • 把 face2.py 推到设备并跑起来
  • 弹一个最小化的 adb 窗口 —— 这个窗口别关，它是保活的命根子

选 2 停止，会杀掉表情屏并把原厂时钟画面还原回去；选 4 是黑屏急救。

为什么不用"杀死原厂 UI"的激进方案

还有一种做法是 kill -STOP lcd 把原厂时钟冻住，这样连 0.125 秒的闪都不会有。 但它有代价：一旦保活的 adb 会话断了，背光可能被写 0，屏幕全黑 —— 上次你遇到的正是这个。 所以默认走共存 + 快速修复：不动原厂进程，代价只是每分钟最多 0.125 秒的闪。 如果你想要彻底无闪，face2.py 也支持 --own 参数切到那个模式。

6还没做的 / 建议

安全：设备出厂 WiFi 密码是公开的弱默认密码，ADB 5555 端口对外开放

同一网段下任何人都能 adb connect 192.168.0.1:5555 直接拿到 root（免认证）， 也能用出厂默认密码连上 WiFi。建议改掉 WiFi 密码，并把 ADB 调试口关掉。

注意：关掉 ADB 5555 之后表情屏就没法推了，两件事是冲突的 —— 要看你更想要哪个。

  • 保活依赖电脑：现在是电脑端挂着 adb 会话。电脑关机、休眠、关掉那个窗口，表情屏就停。 已补了一个 face-keeper.bat —— 它会自动重连、自动重启， 设备重启或链路断了都能自己恢复。 （设备端也有常驻办法 —— mount -o remount,rw / 后写 init 脚本 —— 但那要改系统分区，风险高，没做）
  • 没做：历史趋势落盘（重启后柱状图从零开始）、按客户端分别统计流量、把 SoC 温度写进日志做趋势
  • 顺带发现的：设备负载 load average 常年 7 以上，但 CPU 空闲 78 % —— 说明卡的是等 I/O（调制解调器的 RX_THREAD 长期处于 D 状态），不是 CPU 不够
  • 顺手修掉的：原来的 screen-fix.bat（黑屏急救）用的杀进程模式是 [f]ace.py，而它匹配不上 face2.py —— 因为模式里的 . 得先吃掉那个 2，后面就没字符给 p 了。 也就是说那个急救按钮会静默失效：报告"已停止"但进程还活着。 已改成 [f]ace（两个版本都能杀，且仍然不会误杀自己）。
